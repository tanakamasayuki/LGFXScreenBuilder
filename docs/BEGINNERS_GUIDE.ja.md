## 1. そもそも画面はどうやって光っているのか

PC のグラフィックスとの一番大きな違いは、**MCU 側に「画面そのもの」が無い**ことです。

M5Stack や ESP32 につながっている小型 LCD は、たいてい ILI9341 / ST7789 のような
**コントローラ内蔵パネル**です。パネルの中に画素ぶんのメモリ（GRAM）があり、
表示回路はそこを一定周期で読み出して液晶に出し続けています。MCU がやるのは、

> SPI（または I80 パラレル）で **「この矩形領域に、この画素列を書き込め」** と送りつけること

だけです。送った瞬間にパネル側の GRAM が書き換わり、次のリフレッシュで見えます。

```
  ESP32                          LCD パネル
  ┌──────────────┐   SPI 40〜80MHz   ┌──────────────────┐
  │ あなたのコード │ ───────────────► │ コントローラ      │
  │ lcd.fillRect() │  「x,y,w,h に    │   ↓ 書き込み      │
  └──────────────┘   このピクセル」  │ GRAM（画素メモリ）│
                                      │   ↓ 常時読み出し  │
                                      │ 液晶パネル        │
                                      └──────────────────┘
```

ここから、組み込み描画の性質がほぼ全部導けます。

- **描いた端から見える。** `fillScreen()` して `drawString()` すると、
  「真っ黒になった画面」と「文字が出た画面」の**両方**が順に表示されます。
  PC のようにフレーム単位で切り替わってはくれません。
- **転送量＝時間。** 320×240 の 16bit 全画面は 320 × 240 × 2 = **153,600 バイト**。
  SPI 40MHz なら約 **31 ms**、80MHz でも約 **15 ms** かかります。
  つまり**全画面を描き直す限り、40MHz のパネルでは物理的に 32fps が上限**です。
  これは描画の工夫ではどうにもならない床です。
- **読み戻しは基本できない（遅い）。** 多くの構成でパネルからの読み出しは
  未サポートか非常に低速です。「今の画面の上に半透明で重ねる」が難しいのはこのためです。

### 色は RGB565

送るのは 1 画素 16 ビット、赤 5 / 緑 6 / 青 5 ビットです。
`#4CAF50` のような 24bit 色は必ずこの粒度に丸められます。
グラデーションで縞（バンディング）が出るのはそのせいで、バグではありません。

## 2. なぜちらつくのか

「描いた端から見える」ことの直接の帰結です。よくある更新ループを書くと：

```cpp
void loop() {
  lcd.fillScreen(TFT_BLACK);          // ← ここで画面が真っ黒になる（見える！）
  lcd.drawString("Temp", 10, 10);     // ← 文字が戻ってくる
  lcd.drawString("24.5C", 10, 40);
  delay(100);
}
```

人間の目には、1 秒に 10 回の**黒い瞬き**として見えます。これがちらつきの正体です。
「消してから描く」の**消してから**が見えてしまっている。

素朴な回避策は 2 つありますが、どちらも壁にぶつかります。

**(a) 消さずに、変わった部分だけ上書きする。**
数値が `100` → `99` と短くなると前の桁が残ります。背景を塗ってから書けば、
今度はその小さな矩形だけがちらつきます。パーツが増えるほど
「どこを消すか」の管理が破綻していきます。

**(b) 変化したときだけ描く。**
ちらつく回数は減りますが、1 回ぶんのちらつきは残ります。
アニメーションやリアルタイム値には使えません。

根本の問題は、**画面の更新が原子的でない**ことです。
中間状態が見えてしまう。ならば、中間状態を**見えない場所で**作ればいい。

## 3. ダブルバッファ — と、それが載らない現実

答えははっきりしています。**RAM 上に画面と同じ大きさのバッファを持ち、そこに描き、
完成してから一気にパネルへ転送する。** これがダブルバッファです。
パネルが見るのは完成品だけなので、中間状態は原理的に見えません。

問題は値段です。

| 画面 | 全画面バッファ（16bit） |
| --- | --- |
| 128×128（AtomS3） | 32 KB |
| 135×240（StickC Plus） | 63 KB |
| 240×135（Cardputer） | 63 KB |
| **320×240（Core / Core2）** | **150 KB** |
| 320×480（CoreS3 縦） | 300 KB |
| 720×1280（Tab5） | 1.8 MB |

一方、ESP32 の内蔵 DRAM は約 320 KB、そこから WiFi/BLE スタック・
ヒープの断片化・自分のバッファが引かれます。**320×240 の全画面ダブルバッファは、
載らないか、載っても他に何もできない**のが普通です。
（PSRAM 搭載機なら容量は足ります。ただし後述するように PSRAM は遅く、DMA も効きません。）

これが組み込み GUI の中心的なジレンマです。
**ちらつきを消すにはバッファが要る。バッファを置く RAM が無い。**

## 4. タイル分割ダブルバッファと DMA

妥協点は「全画面バッファを持たず、**画面を横帯（タイル）に切って、1 本ずつ完成させて送る**」です。
[LGFXVirtualCanvas](https://github.com/tanakamasayuki/LGFXVirtualCanvas) がこれをやります。

```
   画面（仮想）                  実 RAM 上のタイルバッファ
  ┌─────────────┐  タイル0        ┌─────────────┐
  │  タイル 0   │ ──描画──────►  │  ~19 KB × 2 │ ──DMA──► パネル
  ├─────────────┤  タイル1        └─────────────┘
  │  タイル 1   │ ──描画──────►      （使い回す）
  ├─────────────┤
  │     …       │
  └─────────────┘
```

320×240 なら、1 行 = 320 × 2 = 640 バイト。既定の目安 19 KB では
19456 / 640 ≈ **30 行**が 1 タイル、つまり **8 タイル**に分割されます。
必要な RAM は 19 KB × 2 枚 = **約 38 KB**。150 KB の 1/4 です。

### あなたの描画関数は「全画面座標」のまま

タイル分割の面倒くささは、普通は自分で書くと座標計算が全部の描画に混ざることです。
LGFXVirtualCanvas は**描画関数を全画面座標で 1 つ書かせて、それをタイルごとに実行**します。
Y オフセットとクリッピングはライブラリ側が隠します。

```cpp
void drawScene(LGFXVirtualCanvas& g) {
  g.fillScreen(TFT_BLACK);
  g.fillCircle(160, 120, 40, TFT_YELLOW);   // ← 全画面座標のまま書ける
}
screen.render(drawScene);                    // ← 中で 8 回呼ばれる
```

**これが一番重要なクセです。** 描画関数は 1 フレームにつき**タイル数だけ実行されます**。
`fillCircle` はタイル外ではクリップで消えるだけなので絵は正しくなりますが、
**関数の中でやった計算やセンサ読み取りは 8 回走ります**（→ [8 章](#8-このライブラリのクセ)）。

### ここで DMA が効いてくる

DMA（Direct Memory Access）は、**CPU を介さずにメモリ ↔ 周辺機器を転送する**ハードウェアです。
LovyanGFX は、内蔵 RAM 上のスプライトを `pushSprite` するとき **非同期 SPI-DMA** を起動し、
**転送の完了を待たずに戻ってきます**。CPU はすぐ次の仕事に移れる。

ここでタイルバッファが 2 枚ある意味が出ます。

```
  時間 ──────────────────────────────────────────►
  CPU:  描画 T0 │ 描画 T1 │ 描画 T2 │ 描画 T3 │ …
  DMA:          │ 転送 T0 │ 転送 T1 │ 転送 T2 │ …
                 ↑ 重なっている
```

タイル 0 を DMA が転送している間に、CPU はもう一方のバッファにタイル 1 を描く（ping-pong）。
結果、**1 フレームの時間 ≈ max(描画の合計, 転送の合計)** になります。
バッファが 1 枚だと、転送中のバッファを上書きすると絵が壊れるので毎回 `waitDMA()` が要り、
**描画 + 転送の足し算**になります。だから LGFXVirtualCanvas は
2 タイル以上の面では自動でダブルバッファを有効にします。

### PSRAM は「遅いけど広い」

タイルバッファを PSRAM に置けば、タイルを大きく（＝分割数を少なく）できます。
描画関数の再実行回数が減るので、**描画が律速なら勝ちます**。ただし、

- PSRAM は内蔵 RAM よりずっと遅い（描くのも読むのも）
- **LovyanGFX は PSRAM 上のスプライトを DMA なしで push します。**
  転送が同期になるので、上の重ね合わせが成立せず、ダブルバッファの意味が消えます

**転送が律速なら負けます。** 無条件に速くなる設定ではないので、実測してください。

## 5. LGFXScreenBuilder ではどう使うのか

ここまでの話を、LGFXScreenBuilder は**設定ではなく include で**切り替えます。

```cpp
#include <M5Unified.h>

#if __has_include(<LGFXVirtualCanvas.h>)
#include <LGFXVirtualCanvas.h>          // ← あるとバッファ描画、無いと直接描画
#endif

#include <LGFXScreenBuilder.h>
#include "MyScreen.h"                    // ← 生成ヘッダはこの後
```

- **`<LGFXVirtualCanvas.h>` を生成ヘッダより前に include すると、タイル分割ダブルバッファ**
- **include しないと、直接描画**
- 実行時の切り替えはありません（`setBuffered()` のような API は無い）

`__has_include` ガードは「ライブラリが未インストールでもビルドは通す」ためのもので、
実際のモードを決めるのは**本当に include されたか**です。

### 効いているかは必ず確認する

**一番ありがちな失敗が include 順の間違い**です。生成ヘッダより後に書くと、
警告もエラーも出ないまま、静かに直接描画のままになります。1 行で確認できます。

```cpp
void setup() {
  M5.begin();
  screen.begin();
  Serial.printf("buffered=%d transparent=%d\n",
                screen.isBuffered(), screen.supportsTransparentScenes());
}
```

### 描画は毎回まるごと

LGFXScreenBuilder に「差分更新」はありません。`show()` は**シーンの全パーツを毎回描き直します**。
これは手抜きではなく、タイル方式と噛み合った選択です。バッファ描画なら
描き直しはユーザーから見えないので、「何を消すか」を管理する必要がそもそも無くなる。

```cpp
Scene::Main main;
main.title   = "Main";
main.battery = "82%";
main.temp    = "24.5C";
screen.show(main);          // 8 タイル ぶん描いて、8 回 DMA で送る
```

### タイル予算を変えたい場合

現在の `Screen` は `LGFXVirtualScreen` を **protected メンバとして持っています**
（`_vscreen`）。公開 API では露出していないので、既定の約 19 KB を変えたいときは
生成された `Screen` を継承してください。

```cpp
struct MyScreenTuned : MyScreen::Screen {
  using MyScreen::Screen::Screen;
#if defined(LGFXVIRTUALCANVAS_H)
  void tune() { _vscreen.setMemoryLimit(40 * 1024); }   // タイルを大きく＝分割を減らす
#endif
};
```

## 6. メモリと速度のトレードオフ表

320×240 / 16bit / SPI 40MHz を例にした目安です（実測は構成次第）。

| 方式 | 追加 RAM | ちらつき | 1 フレームの時間 | 向き |
| --- | --- | --- | --- | --- |
| 直接描画 | 0 | **出る** | 転送のみ ≈ 31 ms | RAM が本当に無い機種、静止画面 |
| タイル + 単一バッファ | ~19 KB | 出ない | 描画 + 転送（直列） | RAM 極小、描画が軽い |
| **タイル + ダブルバッファ**（既定） | **~38 KB** | 出ない | **max(描画, 転送)** ≈ 31 ms〜 | **ほぼ全ての場合の推奨** |
| 全画面ダブルバッファ | 150 KB | 出ない | max(描画, 転送) | PSRAM 機か大 RAM 機のみ |
| タイルを PSRAM へ | 予算次第 | 出ない | DMA 無効・転送が同期 | 描画律速で分割数が多すぎるとき |

覚えておくと判断が速くなる原則：

- **分割数を増やしても描画の合計は減らない。** 増えるのはタイルごとの
  `fillScreen` / `pushSprite` / コールバック再実行のオーバーヘッドだけです。
  タイルは「RAM を減らすための道具」であって、速くするための道具ではありません。
- **転送時間は画面サイズと SPI クロックだけで決まる。** 描画の最適化では下がりません。
- **ちらつきの有無は 38 KB で買える。** 大抵の場合、これは非常に安い買い物です。

## 7. LovyanGFX / M5GFX のクセ

LGFXScreenBuilder を使っていても、overlay を書くと必ず素の API に触れます。
つまずきやすい点をまとめます。

### 描画状態はスティッキー（一番の罠）

`setTextColor` / `setTextDatum` / `setTextSize` / `setFont` は**設定したら残ります**。
どこかで変えると、以降の描画すべてに効きます。

```cpp
g.setTextDatum(middle_center);
g.drawString("A", 100, 60);
g.drawString("B", 100, 90);   // ← こちらも middle_center のまま
```

LGFXScreenBuilder の描画エンジンが Text パーツごとに
font / color / size / datum を**毎回全部設定し直している**のはこのためです
（[Renderer.h](../src/lgfxsb/Renderer.h)）。前のパーツの設定が漏れないようにしています。
自分の overlay でも同じ規律を守ってください。**「今こうなっているはず」を前提にしない。**

### 回転の基準は 0 とは限らない

`setRotation(0)` が「そのボードの標準の向き」とは限りません。M5GFX は
ボードごとに標準回転を設定して `M5.begin()` から戻ります。
LGFXScreenBuilder はこれを吸収していて、`begin()` の時点でボードの標準回転を記録し、
プロファイルの回転を**それに対する相対値**として `(base + profile.rotation) % 4` で適用します。
だから「プロファイルの回転 0 ＝ そのボードの標準の向き」で設計できます。

自分で `setRotation()` を呼ぶ場合は、この基準がずれることに注意してください。

### 色は 24bit で書けるが 16bit に丸められる

`0x4CAF50` のような指定は受け付けられますが、内部で RGB565 に量子化されます。
**「別の色のつもりが同じ色になる」ことが起きえます。**
透過シーンの抜け色チェックが RGB565 に量子化してから比較しているのはこのためです。

### フォントは Flash を食う。CJK は桁違いに食う

LovyanGFX のプリセットフォントは、そのままバイナリに焼き込まれます。
ラテン系は数 KB〜数十 KB ですが、**日本語・中国語・韓国語のフォントは数百 KB〜 MB 級**です。
小さい画面のプロファイルに大きな CJK フォントを有効にすると、
それだけで Flash が足りなくなります。

LGFXScreenBuilder が**フォントをプロファイルごとに有効化**させ、
オーサリングツールが**フォント別の正確な Flash 消費量**を表示するのは、
まさにこの予算管理のためです。

### `startWrite` / `endWrite`

多数の小さい描画を連続で出すときは `startWrite()` / `endWrite()` で囲むと
SPI トランザクションの開始／終了が 1 回にまとまって速くなります。
バッファ描画では LGFXVirtualCanvas が管理するので、
**overlay の中で自分で呼ぶ必要はありませんし、呼ぶべきでもありません。**

### アンチエイリアスとタイル境界

`drawSmoothLine` などの近傍参照を伴う描画は、タイル境界で全画面描画と
完全一致しないことがあります（タイルごとに独立して描画・クリップされるため）。
LovyanGFX の既定プリミティブは AA 無しなので、通常は問題になりません。

## 8. このライブラリのクセ

### overlay はタイル数ぶん呼ばれる ← 最重要

`setOverlay()` で登録した関数は、静的パーツの後に呼ばれます。
バッファ描画では**タイルごとに 1 回、つまり 1 フレームで 8 回走ります**。

したがって overlay は **冪等**（同じ入力 → 同じ絵）でなければなりません。
[examples/OverlayM5Unified](../examples/OverlayM5Unified/) がこの規律の実例です。

```cpp
// ✗ ダメな例：タイルごとに値が変わるので、帯ごとに絵が食い違う
void bad(GFX& g, const Scene::Main& s) {
  int v = analogRead(36);          // タイルごとに読む → 8 個の違う値
  g.fillRect(0, 0, v, 10, 0xF800);
}

// ✓ 良い例：状態は loop() で進め、overlay は「読むだけ」
static int g_value;
void good(GFX& g, const Scene::Main& s) {
  g.fillRect(0, 0, g_value, 10, 0xF800);
}
void loop() {
  g_value = analogRead(36);        // 1 フレームに 1 回
  screen.show(main);
}
```

同じ理由で、overlay の中で **`millis()` / `random()` / センサ読み取り / 通信** を
してはいけません。**重い処理も禁物**です。8 倍払うことになります。

### コールバックは関数ポインタのみ

LGFXVirtualCanvas の制約がそのまま出ます。**キャプチャ付きラムダは渡せません。**
状態は上の例のようにファイル内 static かグローバルで持ってください。

### 画像は「デコード済み」だから安全

overlay の中で `drawPng()` / `drawJpg()` を呼ぶと、**タイルごとにデコードが丸ごと走ります**
（クリップされるのは出力であって、デコードの手間ではない）。8 分割なら 8 倍です。

LGFXScreenBuilder の Image パーツは、オーサリングツールが取り込み時に
**RGB565 の生データへデコードして**ヘッダに焼き込みます。実行時は `pushImage` するだけで、
これはタイルでクリップされます。つまり**このライブラリ経由の画像はこの罠を踏みません**。
自分で PNG を扱うときだけ注意してください（setup で一度だけスプライトへ展開する）。

### 複数の .cpp から使う場合

描画モードは include の有無で**型が変わります**（`Canvas` が
`LGFXVirtualCanvas` か `lgfx::LGFXBase` か）。翻訳単位ごとに include が食い違うと
ODR 違反になりえます。単一の `.ino` なら問題ありませんが、
複数 `.cpp` 構成ではビルドフラグ等でモードをプロジェクト全体に固定してください。

### 静的パーツと overlay の役割分担

- **不変の下地**（グラフの罫線、バーの枠、0% 状態）→ **静的パーツ**
- **文字列**（値が変わるだけで、形は変わらない）→ **静的 Text パーツ ＋ シーン構造体で差し替え**
- **値で形が変わるもの**（バーの塗り、針、波形）→ **overlay**

「ユーザーが書き換える＝ overlay」ではありません。文字列の差し替えは 2 番目です。
また、代表値のバーの塗りなどを静的パーツに焼き込まないでください。
overlay が上書きして二重に見えます。

## 9. 透過シーン（ダイアログ）

「動作中の画面の上に確認ダイアログを出す」ために、画面全体を描き直すのは無駄ですし、
下の画面が一瞬消えます。LGFXScreenBuilder はシーンに**透過**フラグを立てられます。

しくみは単純です。タイルを**抜け色**（既定 `#002400`）でクリアし、
その色を**マスクしながら**パネルへ push します。抜け色のままの画素は転送されないので、
パネルの内容がそのまま残ります。だから角丸ダイアログの**角から下の画面が見えます**。

必要条件と挙動：

| 構成 | 挙動 |
| --- | --- |
| 直接描画 | そのまま動く（背景を塗らないこと自体が透過） |
| バッファ + LGFXVirtualCanvas **1.4.0 以上** | `renderTransparent()` で正しく透過 |
| バッファ + 1.4.0 未満 | `#warning` を出し、**普通の不透明画面**として描かれる |

`screen.supportsTransparentScenes()` で判定できます。

**注意点が 2 つあります。**

1. **閉じるときは、下の画面を自分で描き直す。**
   ライブラリはレイヤを管理しません。ダイアログが触っていない画素は
   誰も復元できないので、`show(下の画面)` を呼ぶのはアプリの責任です。
2. **抜け色で塗ったパーツは「穴」になる。**
   図形ではなく透明部分になります。オーサリングツールが Export 時にこれを検査して警告します。

アルファブレンド（半透明）は**できません**。マスクは画素単位のオール・オア・ナッシングで、
真の合成にはフルフレームバッファかパネル読み戻しが要るからです。

実例は [examples/DialogM5Unified](../examples/DialogM5Unified/) を参照してください。

## 10. 利点と限界

### 向いていること

- **レイアウトをコードから追い出せる。** 座標のマジックナンバーがスケッチから消え、
  ブラウザで見ながら動かせます。文字列 ID も要りません
  （`main.battery = "82%"` が**型付きフィールド**で、綴りを間違えればコンパイルエラー）。
- **1 バイナリで複数機種。** プロファイルごとに独立したレイアウトを持ち、
  `Profile::Auto` が実行時の画面サイズで選びます。Core / StickC / Cardputer を 1 つで。
- **ちらつき対策が include 1 行。** タイル分割・DMA・ダブルバッファの管理は
  LGFXVirtualCanvas 側にあり、ここで書くコードは変わりません。
- **RAM をほぼ食わない。** レイアウトは `PROGMEM` の記述子テーブル（Flash）で、
  実行時のヒープは基本タイルバッファ（約 38 KB）だけです。
- **画面キャプチャで回帰テストできる。** 生成メタデータから host バックエンドで
  全プロファイル × 全シーンを PNG 化できます。
- **AI にレイアウトを頼める。** シーンを自己完結 JSON でコピーして渡せます
  （[AI_LAYOUT_IO.ja.md](AI_LAYOUT_IO.ja.md)）。

### 向いていないこと（設計上の非目標）

- **GUI フレームワークではありません。** ボタン・タッチ判定・フォーカス・
  スクロールビュー・イベントディスパッチはありません。入力処理はアプリ側です。
  それが要るなら LVGL を検討してください。
- **ウィジェットツリー・レイアウトエンジンはありません。** 絶対座標です。
  Flexbox 的な自動配置も、親子関係も、グループもありません。
- **アニメーションエンジンはありません。** 補間・イージング・タイムラインは
  アプリが持ちます。ライブラリは「今この状態を描く」だけです。
- **リテインドモードではありません。** 差分描画の記録はしません。毎回まるごと描きます。
  だから**転送時間の床（40MHz・320×240 で約 31 ms）は消せません**。
  高フレームレートが要るなら、部分更新を自分で書くか
  `LGFXVirtualSprite` で領域を絞る必要があります。
- **半透明・アルファ合成はありません**（[9 章](#9-透過シーンダイアログ)）。
- **パーツ種別は限定的です。** 角丸矩形・直線・円・1 行テキスト・画像のみ。
  多行テキスト、円弧、多角形、テーブルはありません。overlay で自分で描きます。
- **画像スライス・スプライトシート・プロファイル別画像差し替えは現在仕様の範囲外**です。
- **ファイルシステムからの画像読み込みはありません。** 画像は RGB565 で
  ヘッダに焼き込まれるので、**Flash を消費します**。大きな画像を大量に持つ用途には不向きです。

要するに、**「値が入れ替わる、決まったレイアウトの計器盤」に最適化されていて、
「操作できるアプリ UI」ではありません。**

## 11. 困ったときは

| 症状 | 疑うところ |
| --- | --- |
| ちらつく | `screen.isBuffered()` が false ではないか。`<LGFXVirtualCanvas.h>` を**生成ヘッダより前**に include しているか |
| overlay の絵が帯ごとに食い違う | overlay の中で値を読んでいないか。状態は `loop()` で進めて overlay は読むだけに |
| overlay が遅い | タイル数ぶん走っている。重い計算・デコード・通信を外に出す |
| ダイアログを閉じたら跡が残る | 下の画面を自分で `show()` し直す必要がある |
| ダイアログが不透明になる | LGFXVirtualCanvas が 1.4.0 未満。`supportsTransparentScenes()` で確認 |
| ダイアログの一部が消える | そのパーツの色が抜け色（既定 `#002400`）と RGB565 で一致している |
| Flash が足りない | プロファイル別のフォント有効化を見直す。CJK フォントが効いている可能性大 |
| ラムダが渡せない | コールバックは関数ポインタのみ。キャプチャは使えない |
| レイアウトが機種で崩れる | `Profile::Auto` がサイズ一致で解決している。該当サイズのプロファイルがあるか |
| 色が指定と違う | RGB565 への丸め |
