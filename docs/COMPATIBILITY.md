# Compatibility FAQ — when versions do not line up

> 日本語: [COMPATIBILITY.ja.md](COMPATIBILITY.ja.md)

A short guide for "a screen I made earlier no longer works with the new library"
or "someone handed me an old `.h` and it will not build". The full story is in
[SPEC.md](../SPEC.md) §9.2 and §10.1.

## Four things carry a version

| Thing | Where to find it | Role |
| --- | --- | --- |
| **Project file** `*.lgfxsb.json` | `formatVersion` inside the file | **the source of truth** — the design itself |
| **Generated header** `MyScreen.h` | `formatVersion N` in the top comment | derived; can be re-exported |
| **This library** | [library.properties](../library.properties) | the runtime engine that reads the `.h` and draws |
| **LGFXVirtualCanvas** (optional) | `LGFXVIRTUALCANVAS_VERSION_*` macros | buffered drawing and transparent transfer |

## The guarantee has two tiers, and they differ in strength

- **Project file ⇄ authoring tool — strongly guaranteed.** A newer tool reads an
  older `.lgfxsb.json`. This is the source of truth.
- **Generated header ⇄ runtime — best effort.** A newer engine will generally read
  headers produced by older tool versions, but this is deliberately the weaker
  guarantee.

**So there is exactly one guaranteed recovery path: re-export from the project
file.** As long as you still have the `.lgfxsb.json`, opening it in the current
tool and exporting again fixes anything.

## Why an old `.h` still compiles

Descriptors are initialized as **positional aggregates**. New fields are always
**appended at the end**, and the library's structs give them **defaults matching
the old behavior**. Aggregate initialization is valid with fewer initializers than
members, so **an older `.h` that knows nothing about a new field compiles as-is,
and the omitted field takes its default.**

Transparent scenes (§8.16) are the worked example: `SceneDesc::transparent` and
`Project::transparentColor` were appended, and they are **emitted only when a
scene actually uses them** — so a project without transparent scenes generates
byte-for-byte what it did before the feature existed. That is why it did not need
a `formatVersion` bump.

Reordering, removing, or inserting a field in the middle *would* shift positions
and break this. Only then is the data-contract version raised and a re-export
required.

## By symptom

| Symptom | What to do |
| --- | --- |
| Old `.h` fails to compile | Open the `.lgfxsb.json` in the current tool and **re-export**. This is the supported fix |
| You have the `.h` but no `.lgfxsb.json` | If *Embed AI layouts* was on at export time, the layout can be recovered from the comment block at the end of the header (§10.2). If it was off, the layout is gone |
| `#warning "LGFXVirtualCanvas < 1.4.0..."` | Transparent scenes need 1.4.0+ in a buffered build. Update it, or accept opaque rendering |
| A transparent scene renders opaque | Same cause; `screen.supportsTransparentScenes()` will be false |
| Flicker, or `isBuffered()` is false | Not a version problem — **include order**. `<LGFXVirtualCanvas.h>` must come before the generated header |
| Odd link errors across multiple `.cpp` files | If translation units disagree about the include, the `Canvas` type differs and that is an ODR violation. Pin the mode project-wide with a build flag |
| You hand-edited the header and it broke | The `.h` is not meant to be edited — its first line says so. Change it in the tool and re-export |

## Habits that keep this painless

- **Commit the `.lgfxsb.json`.** Version-controlling only the `.h` throws away the
  recovery path above.
- **Treat the `.h` as a build artifact.** Do not hand-edit it; it is stamped
  `// Generated by LGFXScreenBuilder (formatVersion N). Do not edit by hand.`
- **Re-exporting is cheap.** This repository regenerates every example header with
  one command (`node tools/gen-fixtures.mjs --write`) and detects staleness in CI
  with `--check`. You can do the same in your own project.
