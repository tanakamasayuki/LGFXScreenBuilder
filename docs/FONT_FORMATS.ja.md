# フォント形式 — 何を生成でき、それぞれ何を払うか

ジェネレータは **u8g2** / **GFXfont** / **BFF**（1・2・4bpp）/ **VLW**（8bpp）を出力できる。
優劣はなく、それぞれ別のフォントに対する正解である。このページはその選択の根拠で、
フィールド幅は LovyanGFX 自身のソース（`src/lgfx/v1/lgfx_fonts.hpp` / `.cpp`, v1.2.26）から、
サイズと速度は推定ではなく実測から取っている。

English: [FONT_FORMATS.md](FONT_FORMATS.md)

## 結論から

**まず u8g2 で始め、理由があるときだけ動かす。** 1bpp で RAM を使わず、ロード処理も不要で、
LovyanGFX 内蔵フォント自身がこの形式である。CJK セットではこれ以外は現実的でない。

**GFXfont へ動かすのは、u8g2 が欲しいサイズを拒否したとき。** 63px の advance 上限と
255バイト/グリフ上限は u8g2 固有で、GFXfont にはどちらも無い。サイズ帯は同じ 1bpp のまま。
ただし CJK には向かない（理由は自明ではない。後述）。

**BFF か VLW へ動かすのは、アンチエイリアスが欲しいとき。** 小さい文字や斜線を含む字形では
実際に品質が変わる。どちらも定数ではなく実行時に解析される形式で、生成ヘッダが面倒を見るが、
知っておく価値のある帰結がある（「実行時ロード形式」を参照）。

**U+FFFF の壁はどの形式でも外れない。** これは u8g2 の性質ではなく LovyanGFX のテキスト API
の性質である。`IFont::updateFontMetric` も `IFont::drawChar` も `uint16_t` のコードポイントを
取り、全フォント型がそのインタフェースを実装し、`showFont()` は `while (++code < 65536)` で回る。
`decodeUTF8` は 4 バイト列から 21 ビットのコードポイントを組み立てるが、`drawChar` へ渡る際に
切り詰められる。したがって 😀（U+1F600）はどのツールのどの形式でも LovyanGFX では描けない。
BMP 内の絵文字（⌚ ⏰ ☀ ☃ ⚠ ★ ♥）は影響を受けず、既に動く。

## 比較

各列は、ファイル形式が表現しうる値ではなく、**LovyanGFX が実際に課している**上限である。

| | **u8g2** | **GFXfont** | **VLW** | **BFF** |
| --- | --- | --- | --- | --- |
| **本ツールで生成** | **対応（既定）** | 対応 | 対応 | 対応 |
| LovyanGFX の型 | `lgfx::U8g2font` | `lgfx::GFXfont` | `lgfx::VLWfont` | `lgfx::BFFfont` |
| ビット深度 | 1 | 1 | 8（アンチエイリアス） | 1 / 2 / 4（アンチエイリアス）⁸ |
| 扱えるコードポイント | U+0000–U+FFFF | U+0000–U+FFFF | U+0000–U+FFFF | U+0000–U+FFFF |
| グリフの幅・高さ | 127 以下 ¹ | 255 以下 | 255 以下 | 16bit |
| 送り幅 | **−64 〜 63** ² | 0 〜 255 | 0 〜 255 | 16bit |
| 左・上ベアリング | −64 〜 63 ² | −128 〜 127 | −128 〜 127（x のみ） | 16bit 符号付き |
| 行の高さ | 127 以下 ¹ | 255 以下 ³ | 16bit | 16bit |
| 1 グリフのバイト数 | **255 以下** ⁴ | 制限なし | 制限なし | 制限なし |
| 圧縮 | RLE | なし | なし | 任意 |
| カーニング | なし | なし | なし | あり |
| 置き場所 | フラッシュ・`const` | フラッシュ・`const` | フラッシュ＋RAM 索引 | フラッシュ＋RAM 表 |
| 必要バージョン | 任意 | 任意 | 任意 | LGFX 1.2.21+ / M5GFX 0.2.21+ |
| RAM 消費 | **0** | 0 | 9 バイト × グリフ数 ⁵ | フォントごとの表 |
| 使い方 | `setFont(&f)` | `setFont(&f)` | `begin()` でロード ⁹ | `begin()` でロード ⁹ |
| グリフ検索 | ブロックジャンプ表 | **範囲の線形走査** ⁷ | `gUnicode` の線形走査 | cmap サブテーブル |
| `setFont()` の負荷 | ヘッダを読むだけ | **全グリフを走査** ⁶ | — | — |

¹ グリフごとのフィールドは符号なしで、デコーダは最大 8bit まで読む。しかしその容量には
到達できない。**ヘッダ**が `max_char_width` / `max_char_height` を `int8_t` で持ち、
`getDefaultMetric` が `max_char_height` をそのまま `metrics->height` に代入するためである。
127 を超えると負値になり、テキストが上下反転して組まれる。よって実際の上限は 127。

² `get_signed_bits` が `int_fast8_t` を経由するため、符号付きフィールドは 7bit で頭打ちになる。
最初に効いてくるのはこの制約で、実用上の文字高さの上限を書体により 45〜64px 程度に決めている。
`"@" needs dx = 67px … Try a character height of 45px or less` というエラーもこれである。

³ `yAdvance` は `uint8_t` だが、`getDefaultMetric` がアセントとディセントを `int_fast8_t` で
積むため、使える行ボックスは結局 127 程度になる。

⁴ グリフは 1 バイトのジャンプ値で辿るため、255 バイトを超えるエントリは参照できない。
現在はランレングス幅を「これで落ちるグリフが最少になるよう」選ぶので（SPEC §8.7.7）、
通常のサイズでは実害が無くなっている。

⁵ `gBitmap`(4) + `gUnicode`(2) + `gWidth` + `gxAdvance` + `gdX`。PSRAM があればそちら、
無ければヒープに確保される。2,493 グリフなら **22KB の RAM** を恒久的に占有する。

⁶ `GFXfont::getDefaultMetric` は極値ベアリングを求めるため全グリフを走査する。2,500 字の
CJK フォントでは、フォントが実際に切り替わる `setFont()` ごとに全走査になる。u8g2 はヘッダ
7 バイトを読むだけである（`setFont` はポインタが同じなら即 return するので、呼ぶたびではなく
*切り替えるたび*の負荷である）。

⁷ CJK にとって GFXfont の最悪の性質であり、最も気付きにくい点。グリフ表は `EncodeRange` 内の
オフセットで引くため、コードポイントの**連続した並びごとに**範囲が 1 つ必要になる。常用漢字は
飛び飛びなので、既定の選択では**範囲が 1,774 個**になる。`GFXfont::getGlyph` はこの一覧を
**描画する文字ごとに**線形走査する。同じ 2,493 字で実測すると、**1 文字あたり平均 757 回の比較。
u8g2 は 52 回**（ジャンプ表が 64 グリフずつ飛ばすため）。範囲表そのものも下表のフラッシュ量の
うち 10.4 KB を占める。

⁸ ファイル形式としては 8bpp まで表現できるが、LovyanGFX のデコーダが 4 を超える値を拒否する
（`bits_per_pixel %d (LovyanGFX supports 1..4)`）。したがって 8bpp の AA は VLW を意味する。

⁹ どちらも実行時に解析されるため、レイアウト表が指せる定数ではない。生成ヘッダがフォント
オブジェクトとバイト配列の `PointerWrapper`、そして `Screen::begin()` が呼ぶ
`detail::initRuntimeFonts()` を出力する。後述の「実行時ロード形式」を参照。

## サイズ実測

LovyanGFX 同梱の `lgfxJapanGothic_16` を、その 16px のまま各形式へエンコードした結果。
AA の列は被覆値を柔らかくしたものからラスタライズしているので、実際の AA が持つ増分を含む。

| 文字セット | u8g2 | GFXfont | BFF 2bpp | BFF 4bpp | VLW 8bpp |
| --- | --- | --- | --- | --- | --- |
| ASCII 95字 | 1.3 KB | 1.5 KB | 2.2 KB | 3.4 KB | 7.6 KB |
| 全 4,425 字 | 153 KB | 152 KB | 241 KB | 431 KB | 879 KB |

判断はこの一行に尽きる。アンチエイリアスの代金は **2bpp で 1.6倍、4bpp で 2.8倍、
8bpp で 5.7倍**。小さいセットなら数 KB で明らかに払う価値があり、CJK セットでは
フラッシュに入るか入らないかの差になる。

## 速度実測

同一の 6 グリフを、パネル転送に埋もれないようオフスクリーン Sprite へ 300 回描いた。
host x86 での値で、ESP32 では BFF が 1 文字ごとに行う確保の相対コストが上がるため、
絶対値ではなく差の形として読むこと。

| | u8g2 | BFF 2bpp | BFF 4bpp | VLW 8bpp |
| --- | --- | --- | --- | --- |
| 6グリフの `drawString` 1回 | 2 µs | 6 µs | 6 µs | 2 µs |

**VLW は u8g2 と同速**である。サイズから受ける印象とは違うが、被覆値を無圧縮で持つので
描画は単純なコピーになる。**遅いのは BFF** で、`BFFfont::drawChar` は 1 文字ごとに
ヒープを 2 回確保し、グリフを RLE 展開する。16px なら極小の値の 3 倍だが、コストは
グリフ面積に比例するのでサイズとともに増える。64×16 のグリフでは VLW の 28 µs に対して
111 µs を記録した。

つまり「小さくて遅い」対「大きくて速い」ではない。実際は次のとおり。

* **BFF** — フラッシュは安いが、1 文字あたりの CPU を食う。
* **VLW** — フラッシュと常駐 RAM を食うが、CPU ペナルティは無い。

## 実行時ロード形式

u8g2 と GFXfont は `const` オブジェクトで、リンク時点で完成しており、RAM を使わず、
レイアウト表がそのまま指せる。VLW と BFF は違う。LovyanGFX が実行時にテーブルを
ヒープ（あるいは PSRAM）へ展開するため、生成ヘッダはフォント 1 本につきバイト配列・
その `PointerWrapper`・フォントオブジェクトの 3 つと、次を出力する。

```cpp
inline void initRuntimeFonts() { ... }        // namespace detail 内
void begin() { Base::begin(); detail::initRuntimeFonts(); }   // Screen 側
```

ここから 2 つの帰結が出る。

**`screen.begin()` が必須になる。** これが走るまで、それらのフォントはグリフテーブルを
持たない。レンダラはその状態を検知して（`Renderer.h` の `usableFont()`）既定フォントへ
フォールバックするので、`begin()` を忘れたスケッチはヌルポインタを踏まずに素の文字を出す。
ただし出るのは意図と違うフォントである。

**wrapper は全描画より長生きさせる必要がある。** `RunTimeFont::_fontData` はロード時ではなく
*描画時*に読まれるため、生成ヘッダは両方をファイルスコープの static として置く。
`display.loadFont()` を使わない理由もここにある。`LGFXBase` は `_runtime_font` を 1 本しか
持たず、`setFont()` は `_runtime_font.reset()` を呼ぶ。実行時フォントを 2 本使う
プロジェクトでは、片方を描くたびにもう片方が破棄されてしまう。

## アンチエイリアスには背景色が要る

部分的にしか覆われていない画素は、何かに対して合成しなければならない。LovyanGFX はその色を
`_text_style.back_rgb888` から取るが、1 引数の `setTextColor(fg)` は *back を fore と同じ値に
する*。フォント側はこれを「背景塗りなし」と解釈し、`getBaseColor()` へフォールバックする。
その既定値は**黒**である。

したがって黒以外の背景では、base color を設定せずに AA フォントを描くと暗いハロが出る。
レンダラはシーンごとにこれを設定している。

```cpp
g.setBaseColor(_project.background);
```

これはシーン背景の上のテキストに対しては正しく、別の色の Rect の上に載るテキストに対しては
近似になる。加えて次の 2 点を知っておくとよい。

* **VLW は読み出し可能なパネルでは自力で正しくなる。** フレームバッファを読み戻して実画素と
  合成する（`lgfx_fonts.cpp` の "alpha blend mode"）。読み戻せない SPI パネルは多く、
  そこでは他と同じく base color へフォールバックする。
* **BFF は自力では正しくならない。** `draw_alpha_bitmap_common` にその分岐が無い。
* **ハロが見えるのは 4bpp 以上。** 2bpp の最小の非ゼロ被覆は既に 1/3 あり、中間調の背景を
  下回るには強すぎる。

`tests/build_font_formats/` がまさにこれを測っている。

## それでもできないこと

**U+FFFF を超える絵文字**は、どの形式でも描けない。これはフォントファイルではなく
LovyanGFX 自体の変更を要する。
