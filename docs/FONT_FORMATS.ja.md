# フォント形式 — 何を生成していて、形式を変えると何が変わるか

生成機能が出力するのは **u8g2**（`lgfx::U8g2font`）である。この形式には実際の制約があり、
「別の形式にすればその制約は無くなるのか」という疑問が繰り返し出る。このページはそれに答える。
フィールド幅は LovyanGFX 自身のソース（`src/lgfx/v1/lgfx_fonts.hpp` / `.cpp`、v1.2.26）から
取り、サイズは推定ではなく同一のグリフ集合で実測した。

English: [FONT_FORMATS.md](FONT_FORMATS.md)

## 結論から

**U+FFFF の制約は、どの出力形式に変えても無くならない。** これは u8g2 の性質ではなく、
LovyanGFX のテキスト API の性質である。`IFont::updateFontMetric` と `IFont::drawChar` は
どちらも `uint16_t` のコードポイントを取り、すべてのフォント型がそのインタフェースを実装し、
`showFont()` は `while (++code < 65536)` で回る。`decodeUTF8` は 4 バイト列から 21 ビットの
コードポイントを組み立ててはいるが、`drawChar` に渡る途中で切り捨てられる。したがって
😀（U+1F600）は、どのツールで作ったどの形式であっても LovyanGFX では描けない。BMP 内の
絵記号（⌚ ⏰ ☀ ☃ ⚠ ★ ♥）は無関係で、今も動く。

**それ以外の制約は動く。** 送り幅 63px の上限と 1 グリフ 255 バイトの上限は u8g2 固有で、
GFXfont にはどちらも無い。アンチエイリアスには VLW か BFF が要る。それが割に合うかどうかが
このページの残りである。

## 比較

各列は、ファイル形式が表現しうる値ではなく、**LovyanGFX が実際に課している**上限である。

| | **u8g2** | **GFXfont** | **VLW** | **BFF** |
| --- | --- | --- | --- | --- |
| **本ツールで生成** | **対応** | 未対応 | 未対応 | 未対応 |
| LovyanGFX の型 | `lgfx::U8g2font` | `lgfx::GFXfont` | `lgfx::VLWfont` | `lgfx::BFFfont` |
| ビット深度 | 1 | 1 | 8（アンチエイリアス） | 1〜8（可変） |
| 扱えるコードポイント | U+0000–U+FFFF | U+0000–U+FFFF | U+0000–U+FFFF | U+0000–U+FFFF |
| グリフの幅・高さ | 127 以下 ¹ | 255 以下 | 255 以下 | 16bit |
| 送り幅 | **−64 〜 63** ² | 0 〜 255 | 0 〜 255 | 16bit |
| 左・上ベアリング | −64 〜 63 ² | −128 〜 127 | −128 〜 127（x のみ） | 16bit 符号付き |
| 行の高さ | 127 以下 ¹ | 255 以下 ³ | 16bit | 16bit |
| 1 グリフのバイト数 | **255 以下** ⁴ | 制限なし | 制限なし | 制限なし |
| 圧縮 | RLE | なし | なし | 任意 |
| カーニング | なし | なし | なし | あり |
| 置き場所 | フラッシュ・`constexpr` | フラッシュ・`constexpr` | フラッシュ＋RAM 索引 | フラッシュ＋RAM 表 |
| RAM 消費 | **0** | 0 | 9 バイト × グリフ数 ⁵ | フォントごとの表 |
| 使い方 | `setFont(&f)` | `setFont(&f)` | `loadFont(data)` | `loadFont(data, ft_ttf)` |
| グリフ検索 | ブロックジャンプ表 | **範囲の線形走査** ⁷ | `gUnicode` の線形走査 | cmap サブテーブル |
| `setFont()` の負荷 | ヘッダを読むだけ | **全グリフを走査** ⁶ | — | — |

¹ グリフごとのフィールドは符号なしで、デコーダは最大 8bit まで読む。しかしその容量には
到達できない。**ヘッダ**が `max_char_width` / `max_char_height` を `int8_t` で持ち、
`getDefaultMetric` が `max_char_height` をそのまま `metrics->height` に代入するためである。
127 を超えると負値になり、テキストが上下反転して組まれる。よって実際の上限は 127。

² `get_signed_bits` が `int_fast8_t` を経由するため、符号付きフィールドは 7bit で頭打ちになる。
最初に効いてくるのはこの制約で、実用上の文字高さの上限を書体により 45〜64px 程度に決めている。
`"@" needs dx = 67px … Try a character height of 45px or less` というエラーもこれである。

³ `yAdvance` は `uint8_t` だが、`getDefaultMetric` がアセントとディセントを `int_fast8_t` で
積むため、使える行ボックスは結局 127 程度になる。

⁴ グリフは 1 バイトのジャンプ値で辿るため、255 バイトを超えるエントリは参照できない。
現在はランレングス幅を「これで落ちるグリフが最少になるよう」選ぶので（SPEC §8.7.7）、
通常のサイズでは実害が無くなっている。

⁵ `gBitmap`(4) + `gUnicode`(2) + `gWidth` + `gxAdvance` + `gdX`。PSRAM があればそちら、
無ければヒープに確保される。2,493 グリフなら **22KB の RAM** を恒久的に占有する。

⁶ `GFXfont::getDefaultMetric` は極値ベアリングを求めるため全グリフを走査する。2,500 字の
CJK フォントでは、フォントが実際に切り替わる `setFont()` ごとに全走査になる。u8g2 はヘッダ
7 バイトを読むだけである（`setFont` はポインタが同じなら即 return するので、呼ぶたびではなく
*切り替えるたび*の負荷である）。

⁷ CJK にとって GFXfont の最悪の性質であり、最も気付きにくい点。グリフ表は `EncodeRange` 内の
オフセットで引くため、コードポイントの**連続した並びごとに**範囲が 1 つ必要になる。常用漢字は
飛び飛びなので、既定の選択では**範囲が 1,774 個**になる。`GFXfont::getGlyph` はこの一覧を
**描画する文字ごとに**線形走査する。同じ 2,493 字で実測すると、**1 文字あたり平均 757 回の比較。
u8g2 は 52 回**（ジャンプ表が 64 グリフずつ飛ばすため）。範囲表そのものも下表のフラッシュ量の
うち 10.4 KB を占める。

## サイズ実測

既定の選択（ASCII＋かな＋約物＋常用漢字＋単位記号、**2,493 字**、Noto Sans JP）を各形式で
符号化した場合。u8g2 は実際のエンコーダの出力、GFXfont と VLW は同じラスタライズ結果から
各形式のレコード構造で厳密に算出した値である。

| 文字高さ | u8g2 | GFXfont | VLW |
| --- | --- | --- | --- |
| 16px | 103 KB | 99 KB | 635 KB |
| **24px**（既定） | **175 KB** | 189 KB | 1,360 KB |
| 32px | 253 KB | 315 KB | 2,365 KB |

RLE が引き合うのは概ね 20px より上である。16px では GFXfont のほうがわずかに**小さい**。
その大きさのグリフでは、ラン符号化の管理コストが削減分を上回るためである。24px 以上では
u8g2 が勝ち、32px では 20% の差になる。VLW はどちらの 6〜9 倍に加えて 22KB の RAM を要する。
これが 8bpp の代価で、1 ピクセルが 1 バイトになる。

## で、変えるべきか

**GFXfont** — 送り幅 63px の上限と 1 グリフ 255 バイトの上限が無いので、u8g2 が拒否する
大きさまで行ける。20px 未満ではわずかに小さくもなる。ただし対価は文字集合に強く依存し、
CJK ではサイズ表から受ける印象より悪い。

* **グリフ検索が範囲の線形走査** — 1 文字あたり 757 回の比較（u8g2 は 52 回）。常用漢字のような
  飛び飛びの集合では `EncodeRange` が 1,774 個必要になるためである。しかもこれは*描画する*
  文字ごとの負荷、つまり起動時ではなく毎フレームの負荷である。
* **無圧縮** — 32px で 20% 増。サイズを上げるほど差は開く。
* **`setFont()` が全グリフを走査する** — u8g2 がヘッダに持っているメトリクスを、その場で求めるため。
* **一番効く制約はどれも外れない** — BMP 限定は変わらず、行ボックスも `getDefaultMetric` が
  `int_fast8_t` で積むため結局 127 程度のままである。

したがって**大きなラテン表示用フォント**には向く。グリフ数が少なく、範囲は 1〜2 個で済み、
63px の上限にぶつかるのはまさにそういうフォントだからである。逆に、ここで多くの人が生成する
CJK には向かない。前者のための選択肢として追加する価値はあるが、乗り換える理由にはならない。

**VLW** — 現状アンチエイリアスを得る唯一の手段であり、小さいサイズの CJK では画質の差は大きい。
代価が重い。フラッシュ 6〜9 倍に加え、返ってこない 22KB の RAM。少ない文字数（時計や数個の
ラベル）なら妥当だが、常用漢字には払えない。

**BFF** — 紙の上では両取りである。1〜8bpp なのでアンチエイリアスは任意、カーニングあり、
圧縮も任意。ただし新しく未文書で、生成対象にできるほどレイアウトが安定していない。
そして結局同じ `uint16_t` の API を通る。改めて検討する価値はある。

**どれでもない** — U+FFFF を超える絵文字については。これはフォントファイルではなく
LovyanGFX 本体の変更を要する。
