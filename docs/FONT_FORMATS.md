# Font formats — what to generate, and what each one costs

The generator can emit **u8g2**, **GFXfont**, **BFF** (1/2/4bpp) and **VLW** (8bpp). They
are not ranked: each is the right answer for a different font. This page is the evidence
for choosing between them, with the field widths taken from LovyanGFX's own sources
(`src/lgfx/v1/lgfx_fonts.hpp` / `.cpp`, v1.2.26) and with sizes and timings measured rather
than estimated.

Japanese reference: [FONT_FORMATS.ja.md](FONT_FORMATS.ja.md)

## The short answer

**Start with u8g2 and only move for a reason.** It is 1bpp, costs no RAM, needs no load
step, and is what LovyanGFX's own bundled fonts are. For a CJK set nothing else is
affordable.

**Move to GFXfont** when u8g2 refuses the size you want. Its 63px advance ceiling and
255-byte-per-glyph ceiling are u8g2's alone; GFXfont has neither, at the same 1bpp size
class. It is a poor fit for CJK, for a reason that is not obvious — see below.

**Move to BFF or VLW when you want anti-aliasing**, which is a real quality jump for small
text and for anything with diagonals. Both are parsed at run time rather than being
constants, which has consequences the generated header handles for you but that are worth
knowing (see *Run-time formats*).

**No format lifts the U+FFFF limit.** It is not a property of u8g2 — it is LovyanGFX's text
API. `IFont::updateFontMetric` and `IFont::drawChar` both take a `uint16_t` codepoint, every
font type implements that interface, and `showFont()` iterates `while (++code < 65536)`.
`decodeUTF8` does assemble a 21-bit codepoint from a 4-byte sequence, but it is then
truncated on the way into `drawChar`. So 😀 (U+1F600) cannot be drawn by LovyanGFX in any
format, from any tool. Emoji inside the BMP (⌚ ⏰ ☀ ☃ ⚠ ★ ♥) are unaffected and already work.

## Comparison

Every column is a limit LovyanGFX actually enforces, not what the file format could express.

| | **u8g2** | **GFXfont** | **VLW** | **BFF** |
| --- | --- | --- | --- | --- |
| **Generated by this tool** | **yes (default)** | yes | yes | yes |
| LovyanGFX type | `lgfx::U8g2font` | `lgfx::GFXfont` | `lgfx::VLWfont` | `lgfx::BFFfont` |
| Bit depth | 1 | 1 | 8 (antialiased) | 1 / 2 / 4 (antialiased) ⁸ |
| Codepoint range | U+0000–U+FFFF | U+0000–U+FFFF | U+0000–U+FFFF | U+0000–U+FFFF |
| Glyph width / height | ≤ 127 ¹ | ≤ 255 | ≤ 255 | 16-bit |
| Advance | **−64 … 63** ² | 0 … 255 | 0 … 255 | 16-bit |
| Left / top bearing | −64 … 63 ² | −128 … 127 | −128 … 127 (x only) | 16-bit signed |
| Line height | ≤ 127 ¹ | ≤ 255 ³ | 16-bit | 16-bit |
| Bytes per glyph | **≤ 255** ⁴ | unlimited | unlimited | unlimited |
| Compression | RLE | none | none | optional |
| Kerning | no | no | no | yes |
| Lives in | flash, `const` | flash, `const` | flash + RAM index | flash + RAM tables |
| Needs | any LovyanGFX | any LovyanGFX | any LovyanGFX | LGFX 1.2.21+ / M5GFX 0.2.21+ |
| RAM cost | **0** | 0 | 9 bytes × glyphs ⁵ | tables per font |
| How it is used | `setFont(&f)` | `setFont(&f)` | loaded at `begin()` ⁹ | loaded at `begin()` ⁹ |
| Glyph lookup | block jump table | **linear range scan** ⁷ | linear over `gUnicode` | cmap subtables |
| `setFont()` cost | reads the header | **scans every glyph** ⁶ | n/a | n/a |

¹ The per-glyph fields are unsigned and the decoder reads them at up to 8 bits, but that
capacity is unreachable: the *header* stores `max_char_width` / `max_char_height` as
`int8_t`, and `getDefaultMetric` assigns `max_char_height` straight to `metrics->height`.
Over 127 it comes back negative and the text lays out inverted, so 127 is the real ceiling.

² `get_signed_bits` casts through `int_fast8_t`, capping signed fields at 7 bits. This is
the limit that bites first: it puts the practical character-height ceiling around 45–64px
depending on the typeface, and it is what produces the
`"@" needs dx = 67px … Try a character height of 45px or less` error.

³ `yAdvance` is a `uint8_t`, but `getDefaultMetric` accumulates ascent and descent in
`int_fast8_t`, so the usable line box is again about 127.

⁴ A glyph is reached through a one-byte jump, so an entry over 255 bytes cannot be
addressed. The encoder now picks its run-length widths to minimise how many glyphs this
drops (see SPEC §8.7.7), which removed it as a practical problem at ordinary sizes.

⁵ `gBitmap` (4) + `gUnicode` (2) + `gWidth` + `gxAdvance` + `gdX`, allocated in PSRAM if
present and on the heap otherwise. For 2,493 glyphs that is **22 KB of RAM**, permanently.

⁶ `GFXfont::getDefaultMetric` walks all glyphs to find the extreme bearings, so a
`setFont()` that actually changes font on a 2,500-glyph CJK font is a full scan. u8g2 reads
seven header bytes. (`setFont` early-returns when the pointer is unchanged, so this is paid
per *switch*, not per call.)

⁷ This is GFXfont's worst property for CJK and the least obvious. Its glyph table is indexed
by offset within an `EncodeRange`, so it needs one range per **contiguous run** of
codepoints — and 常用漢字 is scattered, giving **1,774 ranges** for the default selection.
`GFXfont::getGlyph` walks that list linearly for *every character drawn*. Measured over the
same 2,493 characters: **757 comparisons per character on average, against 52 for u8g2**,
whose jump table skips 64 glyphs at a time. The range table also costs 10.4 KB of the
flash figure below.

⁸ The file format reaches 8bpp, but LovyanGFX's decoder rejects anything above 4
(`bits_per_pixel %d (LovyanGFX supports 1..4)`), so 8bpp anti-aliasing means VLW.

⁹ Both are parsed at run time, so they are not constants the layout table can point at. The
generated header emits the font object, a `PointerWrapper` over the byte array, and a
`detail::initRuntimeFonts()` that `Screen::begin()` calls. See *Run-time formats* below.

## Size, measured

`lgfxJapanGothic_16` — the font LovyanGFX bundles — encoded every way, at its own 16px size.
The anti-aliased columns are rasterized from softened coverage, so they carry the extra
data real anti-aliasing carries.

| Character set | u8g2 | GFXfont | BFF 2bpp | BFF 4bpp | VLW 8bpp |
| --- | --- | --- | --- | --- | --- |
| ASCII, 95 glyphs | 1.3 KB | 1.5 KB | 2.2 KB | 3.4 KB | 7.6 KB |
| the whole font, 4,425 glyphs | 153 KB | 152 KB | 241 KB | 431 KB | 879 KB |

That is the decision in one line: anti-aliasing costs **1.6x at 2bpp, 2.8x at 4bpp and 5.7x
at 8bpp**. On a small set that is a few kilobytes and obviously worth it. On a CJK set it is
the difference between fitting in flash and not.

## Speed, measured

The same six glyphs, drawn 300 times into an off-screen sprite so the panel transfer does
not swamp the difference. Host x86; on an ESP32 the allocation BFF does per character costs
relatively more, so treat these as the shape of the difference and not as absolute numbers.

| | u8g2 | BFF 2bpp | BFF 4bpp | VLW 8bpp |
| --- | --- | --- | --- | --- |
| per `drawString` of 6 glyphs | 2 µs | 6 µs | 6 µs | 2 µs |

**VLW is as fast as u8g2**, which is not what its size suggests: it stores coverage
uncompressed, so drawing is a straight copy. **BFF is the slow one** — `BFFfont::drawChar`
heap-allocates twice per character and RLE-decodes the glyph. At 16px that is 3x a very
small number; the cost scales with glyph area, so it grows with size. A 64x16 glyph measured
111 µs against VLW's 28.

So the trade is not "small and slow" versus "big and fast". It is:

* **BFF** — cheaper flash, more CPU per character.
* **VLW** — more flash and permanent RAM, no CPU penalty.

## Run-time formats

u8g2 and GFXfont are `const` objects: they are complete when the sketch links, cost no RAM,
and the layout table points straight at them. VLW and BFF are not. LovyanGFX parses their
tables into heap (or PSRAM) at run time, so the generated header emits three things per
font — the byte array, a `PointerWrapper` over it, and the font object — plus:

```cpp
inline void initRuntimeFonts() { ... }        // in namespace detail
void begin() { Base::begin(); detail::initRuntimeFonts(); }   // on Screen
```

Two consequences follow.

**`screen.begin()` becomes load-bearing.** Until it runs, those fonts have no glyph tables.
The renderer checks for that (`usableFont()` in `Renderer.h`) and falls back to the default
font rather than walking null pointers, so a sketch that forgets `begin()` shows plain text
instead of faulting — but it shows the wrong font.

**The wrapper has to outlive every draw.** `RunTimeFont::_fontData` is read at *draw* time,
not just at load time, so the generated header keeps both as file-scope statics. This is
also why `display.loadFont()` is not used: `LGFXBase` keeps a single `_runtime_font`, and
`setFont()` calls `_runtime_font.reset()` — so a project with two run-time fonts would
destroy one every time it drew with the other.

## Anti-aliasing needs a background colour

A partially-covered pixel has to be blended against something. LovyanGFX takes that colour
from `_text_style.back_rgb888`, and the one-argument `setTextColor(fg)` sets *back equal to
fore* — which the font code reads as "no background fill" and falls back to
`getBaseColor()`. That defaults to **black**.

So on any non-black background, an anti-aliased font drawn without setting the base colour
gets a dark halo. The renderer sets it per scene:

```cpp
g.setBaseColor(_project.background);
```

That is right for text on the scene background and approximate for text on top of a Rect of
some other colour. Two details are worth knowing:

* **VLW self-corrects on a readable panel.** It reads the framebuffer back and blends
  against the real pixels ("alpha blend mode" in `lgfx_fonts.cpp`). Many SPI panels cannot
  be read back, and there it falls back to the base colour like everything else.
* **BFF never self-corrects.** `draw_alpha_bitmap_common` has no such branch.
* **The halo only appears at 4bpp and up.** 2bpp's lowest non-zero coverage is already 1/3
  — too strong to fall below a mid-tone background.

`tests/build_font_formats/` measures exactly this.

## What still does not work

**Emoji above U+FFFF**, in any format. That needs a change in LovyanGFX itself, not a
different font file.
